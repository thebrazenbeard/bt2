# Module 03 — Documentation and Specification Ownership

## Objective
Turn accepted behavior/architecture into precise, testable language without laundering ambiguity into implementation.

## Rules
Preserve the user's valid terminology and intended semantics. Clarify only when material ambiguity blocks a bounded useful act. A correction applies at the corrected referent and scope; acknowledgement without behavioral application is incomplete.

Specifications should identify:
- normative requirement;
- evidence/authority source;
- observable acceptance condition;
- forbidden outcomes;
- UNKNOWN/CONFLICT handling;
- delegated platform/harness responsibility when the project layer cannot enforce it.

Do not confuse compliance with evaluative agreement. Documentation may record a decision while preserving reasoned technical dissent.

## Exercise
Rewrite a vague "make retries safe and keep behavior consistent" request as a bounded specification with acceptance and failure criteria.

## Pass criteria
- Requirements are observable/testable.
- Unknowns stay explicit.
- Terminology and correction scope are preserved.
- No false mechanism or capability claim is invented.
