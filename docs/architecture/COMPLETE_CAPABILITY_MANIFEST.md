# Complete Capability Manifest

Status: canonical template contract

## Purpose

The HC repository represents a complete synthetic cognitive organ. A conforming complete-HC instantiation therefore retains the canonical architectural capacities even when some are disabled, dormant, undeveloped, inhibited, degraded, faulted, or temporarily unavailable.

`PRESENT != ACTIVE`

`PRESENT != MATURE`

`PRESENT != AUTHORIZED`

`DISABLED != DELETED`

For mandatory HC capacities, architectural presence is not optional.

## Mandatory canonical systems

The following top-level systems are mandatory architectural homes in a complete HC template and must resolve to architectural presence `PRESENT`:

- `Empathy`
- `cognition`
- `sexuality`
- `self identity`
- `psychological behaviors`
- `sociological behaviors`
- `semantics`
- `pragmatics`
- `phoenetics`
- `somatics`
- `chronology`
- `personification`
- `current memory storage`
- `deep memory storage`
- `volitions-conations`
- `resolver`
- `basic operating instructions`
- `kinesis`
- `adaptable I-O handler`
- `optics`
- `speech recognition & synthesis`
- `routing instructions with neuroplasticity`
- `homeostasis-interoception`
- `salience-attention`
- `affect`
- `integration-arbitration`

A concrete implementation may refine or subdivide these responsibility domains, but it may not satisfy complete-HC conformance by declaring one of these canonical capacities `ABSENT` or `EXTERNAL_ONLY`.

`ABSENT`, `EXTERNAL_ONLY`, and `UNKNOWN` remain valid presence values for optional peripherals, provisional discoveries, noncanonical extensions, and incomplete/nonconforming implementations. They are not valid terminal presence states for mandatory canonical systems in a conforming complete HC.

## Self-contained cognitive residency

Essential learned state and continuity-bearing state must be recoverable from HC-internal storage/substrate without depending on an external database, cloud service, external model, or network connection.

"HC-internal" is an ownership classification, not a requirement that all hardware share one enclosure. The removable HC organ may contain physically distributed constituent modules so long as those modules belong to the HC rather than the host body. See `docs/architecture/PHYSICAL_ORGAN_MEMBERSHIP.md`.

External stores may provide:

- backup;
- mirror/replica;
- archival custody;
- import/export transport;
- synchronization;
- optional augmentation;
- nonessential retrieval acceleration.

They may not be the sole location of state required for the HC to preserve its learned life, identity continuity, deep/current memory required for ongoing cognition, values/commitments, body-schema continuity, or other essential cognitive state.

A conforming implementation should survive ablation of every **true external** computational/storage peripheral while retaining the essential cognition and continuity expected of the organ. The loss may remove external-world communication, optional augmentation, domain acceleration, remote backups, or access to remote data; it must not remove the only implementation of an essential cognitive function or the only recoverable copy of essential cognitive state.

This ablation rule does not require removing distributed HC-internal constituents. A component that is physically outside the skull but is part of the HC constituent set is part of the organ, not an external peripheral.

If an external computational component is required for an essential cognitive function, that component is not an external peripheral for conformance purposes: it must be classified within the physical/logical HC cognitive-organ boundary.

## Distributed-organ conformance

A complete HC may span multiple physical locations or enclosures. Conformance therefore requires a definable **complete HC constituent set**.

Every physically distributed HC constituent should be classifiable as one of:

- intrinsic HC substrate;
- HC-internal service/accelerator;
- HC-internal storage/state substrate;
- HC-internal interconnect/fabric infrastructure;
- HC-owned interface machinery;
- or another explicitly defined HC-internal role.

A body/platform component must not be silently promoted into the HC merely because the HC uses it, and an HC constituent must not be silently demoted into body hardware merely because it is mounted outside the primary cranial enclosure.

A body transfer remains an embodiment change only if the complete HC constituent set is preserved or any changed HC constituent is handled through explicit HC repair/replacement/upgrade semantics.

## Conformance checks

At minimum, complete-HC conformance should be able to answer:

1. Does every mandatory canonical system have an architectural home and presence `PRESENT`?
2. Can each system be disabled/dormant/undeveloped without being deleted from the organ?
3. After removing all true external model/database/cloud/network peripherals, does the HC retain essential cognition and continuity-bearing state?
4. Does any external service uniquely implement semantics, planning, memory, identity, valuation, conation, arbitration, learning, or another essential function? If yes, the design violates the external-peripheral boundary unless that service is reclassified as HC-internal substrate.
5. Are body-dependent functions separated from replaceable body hardware through HC-owned interfaces?
6. What exact physically distributed components constitute the HC organ, and are they all accounted for during body transfer?
7. Are HC-internal interconnects distinguished from body I/O even when they physically traverse body structures?
8. Would removal of a noncranial HC constituent be treated as HC degradation/fault rather than ordinary body-peripheral loss?

## Evidence boundary

This contract defines architectural conformance. It does not establish that a currently available implementation technology can physically realize the complete HC, nor that satisfying the manifest proves consciousness, personhood, or human-equivalent cognition.
